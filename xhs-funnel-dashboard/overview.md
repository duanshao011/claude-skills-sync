# 小红书全链路投放看板：架构审查

## 结论

这是一个“Python 离线数据处理 + 原生 JavaScript 单页展示”的单文件看板：四类业务表先被清洗、统一字段并按笔记 ID 合并，再将结果、CSS、JavaScript 和本地 ECharts 一次性内联为可双击打开的 HTML。

整体分层是清楚的，适合无服务端、反复覆盖生成的使用方式。当前主要问题不在技术选型，而在“业务契约、模板和实现出现漂移”，加上缺少自动化回归测试，导致修一处容易碰坏另一处。

## 整体数据流

```text
蒲公英 / 星河 / 薯条 / 灵犀
            │
            ▼
build_dashboard.py
目录扫描、参数处理、加载状态、周期对齐检查
            │
            ▼
loaders.py + column_map.py
列名容错 → 清洗 → 口径过滤 → 标准 DataFrame
            │
            ▼
metrics.py
按 note_id 合并 → 派生指标 → P25/P75 水位线
→ 单篇/汇总趋势 → 成本时序 → KPI
            │
            ▼
render.py
构建 JSON payload，内联模板、CSS、JS、ECharts
            │
            ▼
全链路投放看板.html
浏览器内完成图表、筛选、联动、排序、分页、导出
```

## 文件职责

| 文件 | 职责 |
|---|---|
| `scripts/build_dashboard.py` | CLI 主入口；扫描文件、加载四表、计算、生成 HTML、打印回执 |
| `scripts/column_map.py` | 四表字段别名与蒲公英列号兜底 |
| `scripts/loaders.py` | 每张表独立读取、清洗、口径锁定、聚合 |
| `scripts/metrics.py` | 主表关联、业务指标、水位线、趋势和成本数据 |
| `scripts/render.py` | 字段元数据、默认列、payload 序列化、资源内联 |
| `assets/template.html` | 页面 DOM 骨架 |
| `assets/dashboard.js` | 全部前端状态、图表、搜索联动、表格和导出逻辑 |
| `assets/dashboard.css` | 页面主题、响应式、图表区、冻结表头/列、弹窗样式 |
| `assets/echarts.min.js` | 本地 ECharts，保证成品零外链 |

## 前端状态结构

- `DATA`：Python 注入的只读业务数据。
- `STATE`：三个模块的联动开关与当前笔记。
- `TABLE`：展示列、排序、关键词、查询条件、分页。
- `MODAL`：自定义列弹窗草稿状态。
- 三个 ECharts 实例：日汇总、单篇趋势、单篇成本。
- `localStorage`：保存目录折叠状态和用户自定义列。

前端没有框架和构建步骤，部署成本低；代价是 `dashboard.js` 已约 2200 行，状态和 DOM 操作高度集中，后续修改的回归风险偏高。

## 当前确认的关键风险

### P0：查询面板实现存在，但页面模板没有对应 DOM

`dashboard.js` 已实现 `qpCreator / qpNoteId / qpDateStart / qpDateEnd / qpQuery / qpReset / qpExport`，CSS 也有完整样式，但 `template.html` 没有这些元素。`initQueryPanel()` 因此直接返回，查询面板和 CSV 导出实际不会出现。

### P0：四表“任意组合可生成”与主表构造逻辑冲突

`metrics.py:build_master()` 的主体只取“星河 ∪ 薯条”。如果只上传蒲公英或只上传灵犀，最终主表为空，与项目核心契约不一致。

### P1：多份薯条表可能重复累计

扫描逻辑会保留全部薯条文件，之后按笔记 ID 对数值列直接求和。若两份文件日期重叠或是重复导出，会重复计算投放金额。星河有 `(note_id, date)` 去重，薯条目前没有等价的稳定去重键。

### 已修复：薯条金额字段已锁定为“实际支付金额”

投放金额现在只读取薯条“实际支付金额”，并仅保留订单状态为“推广完成”的记录。不再识别或回退到“实际消耗”；缺少“实际支付金额”列时，薯条表会明确加载失败，避免金额口径悄悄变化。

### P1：成本时序采用近似自然日对齐

薯条“启动日”与星河“归因成交日”按相同日期拼接。该方法适合观察趋势，但不能被当作严格的当日投放效率；累计成本曲线可能受归因滞后影响。

### P2：说明文档、模板编号和实现存在漂移

看板已增加“日维度进店趋势”，现有注释仍混用“图表一/二/三”；SKILL 中部分结构描述与当前模板不一致。继续迭代前应统一页面模块定义。

### P2：缺少自动化回归测试

目前只有 Python/JavaScript 语法检查、周期对齐提示和人工 Edge 截图自检。缺少：

- loader 字段漂移测试；
- 四表 16 种上传组合测试；
- 指标公式测试；
- payload 契约测试；
- 前端 DOM 存在性与关键交互测试；
- 冻结列横滚截图回归。

## 架构优点

1. 四个 loader 独立，业务表变化能局部处理。
2. 字段口径元数据由 Python 注入，表头说明与数据结构基本同源。
3. 成品单 HTML、ECharts 本地化，适合直接分发和反复覆盖。
4. 缺表状态、行级来源标记、水位线方向等业务表达已经比较完整。
5. 表格筛选、排序、分页、自定义列都在浏览器内完成，当前数据规模无需后端。

## 建议的修复顺序

1. 先补回查询面板 DOM，恢复筛选和导出。
2. 修正主表主体为四表 ID 并集，真正满足任意组合。
3. 统一薯条多文件去重策略和必需字段校验。
4. 给 loader、指标公式、四表组合和 payload 加最小测试集。
5. 最后再拆分 `dashboard.js`，避免在业务问题未稳定前做大重构。
