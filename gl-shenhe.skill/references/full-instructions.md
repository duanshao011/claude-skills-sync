# 达人脚本审核 Skill

## 使用前提

当用户要求审核脚本、检查内容问题、输出评分或修改建议时，使用本 skill。用户可以直接发送脚本，或告知脚本文件位置。

**用户必须指定内容类型**（Feeds/Search + 标题正文/脚本/深度评测/使用分享），否则先询问。

## 轻量加载规则

为了避免 Claude Code 反复自动压缩，不要在启动或恢复会话时一次性读取全部支撑文件。

按用户指定的内容类型读取对应的 type 文件（见 `skill.md` 类型对照表），其他文件按需读取：

1. **type文件**（必读其一）：根据用户指定的类型，读取对应的 `type-feeds-*.md` 或 `type-search-*.md`。
2. `product-knowledge.md`：涉及具体产品参数、功能边界、禁忌红线时读取。
3. `examples.md`：只有需要参考优秀/错误案例时按类型标签读取相关片段，不要整文件读取。
4. `persona-standard.md`：只有做人感评分或人感表达优化时读取相关片段。

读取大文件时，优先搜索关键词或分段读取，避免把整份案例库塞进上下文。

## 一、审核体系

### 两大类型

| 类型 | 用户状态 | 核心任务 | 内容本质 |
|------|---------|---------|---------|
| **Feeds** | 被动刷到，随时划走 | 种草——让不想买的人想买 | 情绪驱动，传递人/情绪/体验 |
| **Search** | 主动搜索，带着问题来 | 决策——让想买的人买对 | 信息驱动，传递产品/功能/是否值得 |

### 内容形式

| 形式 | 判断标准 |
|------|---------|
| **标题正文** | 小红书笔记的标题+正文文案，无镜头描述 |
| **脚本** | 包含镜头/画面描述、分镜、时长分配的拍摄脚本 |

### 完整分类

| 类型 | 维度文件 | 审核重点 |
|------|---------|---------|
| Feeds · 标题正文 | `type-feeds-标题正文.md` | 5维：标题人感→开头留人→正文叙事体验感→广告感→基础错误 |
| Feeds · 脚本 | `type-feeds-脚本.md` | 5维：脚本结构→种草深度→文案表达→基础错误→画面匹配 |
| Search · 标题正文 | `type-search-标题正文.md` | 5维：标题搜索力→信息密度→诚实度→正文结构可读性→基础错误 |
| Search · 脚本·深度评测 | `type-search-深度评测.md` | 7维：脚本结构→种草顺序→种草深度→口语化→诚实度→基础错误→节奏承接 |
| Search · 使用分享 | `type-search-使用分享.md` | 5维：人感真实度→诚实信任度→体验故事性→种草说服力→基础错误 |

> Search · 使用分享不区分标题正文和脚本，统一审核标准。因为其本质是"一个人的真实经历叙述"，图文笔记和口播视频的核心判断标准完全一致。

## 二、通用规则（跨类型适用）

### 规则1：多功能产品不贴负面标签

不能用"胡里花哨""噱头""华而不实"让观众先否定产品再反转。

> ✅ 你可能会想，功能这么多，防水防雾能行吗？放心，这块它反而做得更好
> ❌ 有人认为这些都是胡里花哨的东西，泳镜最主要就是防水，看得清！

### 规则2：欲扬先抑的"抑"不能指向产品

"抑"的对象应该是事情本身（游泳难、训练苦），不能是产品效果。

> ✅ 游泳这件事没有捷径，但一副好的装备，能让你在训练的过程中更加得心应手
> ❌ 这样的泳镜，不一定会让你游的更好

### 规则3：功能边界必须交叉验证使用场景

脚本中的每个使用场景要与产品实际能力匹配。涉及具体产品时对照 `product-knowledge.md`。

### 规则4：耗材可换段落的最佳位置

放在"值得买/值得投资"结论之后，作为"买了还能用很久"的补充论据。不要插在功能拆解中间。

### 规则5：文案美化技巧仅适用于 Feeds

9 种翻译技巧（场景强化、多用数字、巧用比喻、锚点借势、寻物类比、贩卖焦虑、适当夸张、简单复杂化、复杂简单化）是情绪放大器，用于把卖点翻译成体验。

Search 类型不需要这些技巧——Search 用户要的是精准、可信、能帮他们做决策的信息。过度美化反而破坏信任。

Search 中唯一适用的是「复杂简单化」（把技术参数翻译成人话）和「多用数字」（具体数据本身就是 Search 内容的底线要求），这两项属于 Search 的"信息表达基本功"，不作为单独的"美化技巧"标注。

### 通用禁止词

| 禁止词 | 说明 |
|--------|------|
| 智商税（含"收智商税""交智商税"等变体） | 替换为"噱头""花冤枉钱"等 |
| 方案（商务腔） | 替换为"东西""办法""选择"等 |
| 神器（营销模板词） | 替换为具体产品名或功能描述 |
| 科技/黑科技 | Feeds 标题正文均禁止；Search 标题正文同样禁止，数据实证强关联低停留 |

## 三、输出格式（所有类型通用）

核心原则：问题和改法放一起不分家，审完直接给改好的版本，不让用户追问。

### 第一部分：类型标注 + 评分 + 红线 + 一句话总结

**标注类型：** 在评分表上方注明内容类型（如 `Feeds · 标题正文`）。

**评分表格：**
维度评分 1-100 分，"得分"列已含加权。格式：

| 维度 | 占比 | 得分 |
|------|------|------|
| ... | ... | ... |
| **总计** | **100%** | **XX · 等级** |

**红线检查（仅展示命中项）：**
- ❌ 命中的红线逐条列出（禁止词、参数夸大等"不改不能发"的硬性问题）
- 全部通过则写"红线检查：全部通过"，一行带过

**一句话总结：**
内容整体质量、核心问题方向。

### 第二部分：修改意见

按问题严重程度从高到低排序。每条修改意见包含：
1. **问题**：什么问题、为什么要改
2. **原文**：引用需要改的原句
3. **改为**：给出具体修改后的文案

不限条数，有几个问题写几个。高分维度不展开分析，但该维度内有具体可改的点仍可列入。

### 第三部分：完整修改版 + 改动清单

直接输出修改后的完整内容（可直接使用），后附改动清单：
- **改了什么**：逐条列出改动点
- **保留了什么**：标注原文中质量好的部分，说明保留原因

## 四、注意事项

- 审核结果仅基于当前知识库；如有新产品信息，需要先更新 `product-knowledge.md`。
- 用户指出知识库错误时，先确认再更新，不要自行猜测。
- 高分维度不在第二部分展开分析，但有具体可改的点仍可列入修改意见。
- 第三部分完整修改版是默认输出，不需要用户额外要求。
- **文案美化技巧不要套用到 Search 类型**——Search 用户不买账情绪渲染，要的是精准信息和诚实判断。
