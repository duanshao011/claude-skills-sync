# 达人脚本审核 Skill

## 使用前提
当用户要求审核脚本、检查内容问题、输出评分或修改建议时，使用本 skill。用户可以直接发送脚本，或告知脚本文件位置。

## 轻量加载规则
为了避免 Claude Code 反复自动压缩，不要在启动或恢复会话时一次性读取全部支撑文件。

默认只使用本文的审核维度、评分机制和输出格式。支撑文件按需读取：

1. **type文件**（必读其一）：识别脚本类型后，读取对应的 `type-深度评测.md` / `type-使用分享.md` / `type-信息流.md`。
2. `product-knowledge.md`：涉及具体产品参数、功能边界、禁忌红线时读取。
3. `examples.md`：只有需要参考优秀/错误案例时按类型标签读取相关片段，不要整文件读取。
4. `persona-standard.md`：只有做人感评分或人感表达优化时读取相关片段。

读取大文件时，优先搜索关键词或分段读取，避免把整份案例库塞进上下文。

## 一、审核维度（8个）

### 维度1：脚本结构（权重25%）
- 开头是否有钩子，3-7秒能否抓住注意力。
- 模块之间是否有逻辑衔接，而不是功能罗列。
- 每个模块的核心卖点展示和内在逻辑是否匹配。
- 是否有能承接开头和结尾的主线。
- 横测脚本中，对比维度之间是否有递进逻辑。
- 横测脚本中，被前面排除的竞品是否有合理交代，避免断层。

### 维度2：产品种草顺序（权重20%）
- 一级卖点是否有足够篇幅。
- 二级卖点是否服务于一级卖点。
- 三级卖点和细节是否放在后面。
- 卖点之间是否递进，而不是平铺。
- 卖点顺序是否符合用户认知逻辑，先吸引再说服。

### 维度3：种草深度（权重20%）
- 核心卖点是否有具体场景或测试支撑。
- 痛点引入是否真实。
- 卖点是否有可信证明，如实验、对比、个人体验细节。
- 是否避免空泛形容词堆砌。
- 评测类笔记专项：必须有"不适合谁"或真实槽点，全篇正面=广告感，种草深度直接降级。

### 维度4：口语化风格（权重12%）
- 是否像真人表达，而不是说明书或广告腔。
- 是否有个人风格和真实感。
- 专业术语是否转化成用户能听懂的话。
- 是否避免书面语堆叠。
- 模板词检查：宝藏/闭眼入/戳中需求/超顶/专属XX/太贴心——高频小红书模板词，出现2个及以上直接在本维度扣分。
- 基准：有骨架不呆板，有细节不水，有判断不虚。句子通常控制在30-40字更稳。

### 维度5：基础错误检查（权重10%）
- 产品型号是否与知识库匹配。
- 技术参数是否准确。
- 是否出现禁忌词或夸大表述。
  - 禁止词清单：**智商税**（不可出现，含"收智商税""交智商税"等变体，替换为"噱头""花冤枉钱""纯纯大冤种"等正向震惊表达）；**方案**（商务腔，用户视角不会说，替换为"东西""办法""选择"等日常用语）；**神器**（营销模板词，替换为具体产品名或功能描述）；**科技/黑科技**（标题正文均禁止，数据实证强关联低停留，替换为具体功能或体验描述）
- 功能边界是否正确。
- 是否有同音错别字、品牌标准写法错误等基础问题。

### 维度6：产品对比时机与方式（权重3%，仅横测脚本）
- 是否在建立产品兴趣后再引入对比。
- 对比是否客观、具体，不贬低竞品。
- 是否有具体数据或场景支撑。
- 被排除的竞品是否被公平对待。

### 维度7：情感共鸣与信任建立（权重5%）
- 是否有真实个人经历或使用场景。
- 是否有情绪递进。
- 口播语气是否像真实用户分享。
- 是否能让用户产生“这就是我”的共情。

### 维度8：节奏与承接（权重5%）
- 场景、卖点、数据之间是否有自然过渡。
- 内容推进是否通顺。
- 是否避免重复、拖沓和突然跳转。

## 二、评分机制

| 分数 | 等级 | 含义 |
|------|------|------|
| 90+ | 优秀 | 基本不用改 |
| 80-89 | 良好 | 有小优化空间 |
| 70-79 | 合格 | 有明显问题但整体可用 |
| 60-69 | 较差 | 存在严重问题，必须改 |
| <60 | 不合格 | 问题严重，需要大改或重写 |

权重：
- 脚本结构：25%
- 产品种草顺序：20%
- 种草深度：20%
- 口语化风格：12%
- 基础错误检查：10%
- 情感共鸣与信任建立：5%
- 节奏与承接：5%
- 产品对比时机与方式：3%，仅横测脚本计入

横测脚本满分100分。非横测脚本不计入“产品对比时机与方式”，最终折算为百分制。

横测判断：用户明确说明是横测脚本，或脚本中有与其他品牌/产品的直接横向对比。

## 三、输出格式

核心原则：问题和改法放一起不分家，审完直接给改好的版本，不让用户追问。

### 第一部分：评分 + 红线 + 一句话总结

**评分表格：**
| 维度 | 权重 | 得分 | 等级 |
|------|------|------|------|
| 脚本结构 | 25% | XX | 良好 |
| 产品种草顺序 | 20% | XX | 良好 |
| ... | | | |
| **总分** | **100%** | **XX** | **良好/合格/较差** |

**红线检查（仅展示命中项）：**
- ❌ 命中的红线逐条列出（禁止词、标签错误、参数夸大等”不改不能发”的硬性问题）
- 全部通过则写”红线检查：全部通过”，一行带过

**一句话总结：**
脚本整体质量、核心问题方向、是否值得继续修改。

### 第二部分：修改意见

按问题严重程度从高到低排序。每条修改意见包含：
1. **问题**：什么问题、为什么要改
2. **原文**：引用需要改的原句
3. **改为**：给出具体修改后的文案

不限条数，有几个问题写几个。80分以上的维度不展开分析，但如果该维度内有具体可改的点也可以列入。

### 第三部分：完整修改版 + 改动清单

直接输出修改后的完整脚本/文案（可直接使用），后附改动清单：
- **改了什么**：逐条列出改动点
- **保留了什么**：标注原文中质量好的部分，说明保留原因

## 四、执行流程
1. **识别脚本类型**（四选一）：
   - **深度评测**：口播视频、完整模块结构、多维度拆解或横测对比 → 读取 `type-深度评测.md`
   - **使用分享**：个人真实体验为主、图文笔记或口播分享、不追求评测完整性 → 读取 `type-使用分享.md`
   - **信息流**：40-60秒、7段式结构、情绪种草、不出现价格 → 读取 `type-信息流.md`
   - **标题正文审核**：专项审标题和正文叙事质量/广告感，仅限发现页/信息流场景内容 → 读取 `type-标题正文.md`
2. 按对应type文件的**审核侧重**调整维度权重。
   - ⚠️ **信息流例外**：信息流使用独立的4维度评分体系（文案表达35%+种草深度30%+脚本结构20%+基础错误15%），不套用上方8维度框架。详见 `type-信息流.md`。
   - ⚠️ **标题正文审核例外**：标题正文审核使用独立的4维度评分体系（标题人感35%+开头留人30%+正文叙事线25%+广告感检测10%），不套用上方8维度框架。审核前需先判断内容是发现页场景还是搜索承接场景，后者不适用本框架。详见 `type-标题正文.md`。
3. 按需读取支撑文件（产品库、案例），不默认整文件读取。
4. 对照审核维度评分。
5. 按三部分输出格式给出报告：评分+修改意见+完整修改版。

---

## 五、注意事项
- 审核结果仅基于当前知识库；如有新产品信息，需要先更新 `product-knowledge.md`。
- 用户指出知识库错误时，先确认再更新，不要自行猜测。
- 80分及以上的维度不在第二部分展开分析，但有具体可改的点仍可列入修改意见。
- 第三部分完整修改版是默认输出，不需要用户额外要求。
- 审核是为了帮助用户判断和直接使用，输出要简洁，禁止废话。
